# Agent packaging and service decision

Phase 5 provides a development executable and offline Ed25519 package verifier. It does not install a background service, download updates, configure a signing provider or create release signing credentials. Release distribution remains gated on provider/key ownership, code signing, notarization and installer acceptance.

## Release trust and replacement

Ship the matching Go binary in Electron `resources/agent/netsentry-agent` on the initial macOS target. The renderer cannot choose this path. Development builds alone accept a main-process environment override. Electron verifies ownership/file permissions before invoking the credential helper, but those checks are **not** code-signature verification. Release packaging must verify the signed application/binary chain before first execution; ordinary developer-built binaries are not distribution-verified.

Use an offline-controlled Ed25519 root whose public key is pinned in the installer. Sign exact UTF-8 manifest bytes; publish a detached signature and the artifact. Each manifest includes `schemaVersion:1`, positive monotonic `release`, semantic display `version`, exact `platform`/`architecture`, artifact basename, `bytes`, lowercase SHA-256, and UTC-millisecond `expiresAt`. Metadata expires within 30 days. The Go verifier checks all these bindings and an operator-supplied minimum release. It never executes or installs the file.

The future installer must persist a protected accepted-release high-water mark across upgrades/reinstallation; the CLI minimum is an input, not persistent rollback protection. Download to a separate staging path, verify using the pinned key, verify platform code signing, stop the user agent, atomically replace the application-owned binary and restart only if background permission remains. Verify the same opened bytes at replacement time; the current CLI verification result must not authorize a later mutable file. Preserve credentials/state outside the application bundle. Keep the previous signed version for health rollback; rollback must satisfy explicit signed recovery policy and must not erase the high-water mark silently. Key rotation needs a root-signed transition and acceptance tests. None of these installer actions is enabled now.

## Explicit service registration

The desktop implements explicit registration, start and removal for a macOS **per-user LaunchAgent**, with no root/LaunchDaemon registration. The fixed label is `com.netsentry.agent`; the private plist is `~/Library/LaunchAgents/com.netsentry.agent.plist`. Registration requires the signed packaged app and matching agent, a configured signing team and installation at `/Applications/NetSentry.app` or `~/Applications/NetSentry.app`. Unsigned preview builds cannot register. Opening the app never installs or starts a service.

Register/Start requires native confirmation with Cancel selected by default. Confirmation permits saving local background consent only after a fresh workspace grant with matching pairing generation. The agent helper takes the runtime lock and preserves other preferences and credentials. A foreground agent must be stopped first. Login startup independently repeats local and fresh workspace checks before launching monitoring workers; stale generation requires foreground reconciliation. Module and shutdown permissions remain separate.

The plist contains only fixed executable arguments (`run --background --state-dir`), a private state path, `RunAtLoad=true`, `KeepAlive=false`, an Aqua session restriction and private umask. It runs no shell, embeds no credentials and sends standard output/error to `/dev/null`. If login occurs offline or permission is denied, the agent exits; reconnecting does not automatically restart it. Resolve the cause and explicitly select Start.

A private desktop receipt binds the original binary, state directory and exact plist hash. Registration refuses unknown jobs/files, unsafe permissions, symlinks and stale sockets. Files are published exclusively and atomically; partial failures retain ownership evidence for retry/removal. Status distinguishes registration, loaded job and process running; none proves monitoring accuracy. Removal confirms ownership again after the dialog and after bootout, stops only the owned job, verifies absence and deletes only matching files. It preserves pairing, modules, sharing settings and stored data. Clearing local background permission uses the signed helper without requiring backend access; if unavailable, the UI explicitly reports that consent could not be cleared. Owned service removal remains available when signature trust is lost, without executing an untrusted helper.

Updates require service removal before replacement and never re-register automatically. The runtime lock serializes helper mutations with foreground/background agents; the desktop serializes updates and service actions. After updating, explicitly register again. Remove before moving/deleting the application. Conflicting files/jobs require operator review; the app never kills an unknown PID or silently repairs a stale socket.

A hard crash can leave `agent.sock`. Startup refuses to replace it. After confirming the foreground process has exited, an operator may remove only the private socket and restart; normal shutdown removes its own socket. An installer should provide a process-identity-aware repair workflow, not delete arbitrary paths.

Windows named-pipe ACL, private-state ACL, runtime locking and explicit user service/login registration are deferred together. Credential Manager source exists but is not runtime accepted. Linux development tests use Unix sockets and explicit loopback-only file storage; production Secret Service and service supervision remain unimplemented. No TCP fallback is permitted. Phase 6 process adapters and Phase 7 remote command delivery remain independent gates.

Phase 14 supplies offline Ed25519 candidate packaging and protected per-target verification high-water state in `infra/scripts/release.mjs`, compatible with the existing Go verifier. This verifies candidates only; it does not install/update binaries or satisfy OS code signing, service installation or atomic replacement/rollback. Follow the Phase 14 operational runbook before preparing a distributable release.

## Desktop packaging/update implementation

The desktop now has pinned electron-builder 26.18.0/electron-updater 6.8.11 source, local preview packaging, signed DMG/ZIP release configuration and a mandatory Ed25519 signed-JSON provider with persistent high-water state. It delegates replacement/relaunch to macOS Squirrel instead of implementing a shell/file-swap installer. Runtime trust verifies app and bundled agent code signatures against the configured team before credential-helper execution. An internal agent update-lock helper excludes the existing runtime lock during handoff. No production identity/host is configured, so updates and unsigned packaged-agent execution remain disabled. Explicit service registration/removal is implemented separately as described above; no service is registered automatically and no automatic agent restart is implemented. See [packaging runbook](../../desktop/packaging/README.md) and [available verification](../validation/desktop-packaging.md). Native signed replacement/recovery remains an acceptance gate.
